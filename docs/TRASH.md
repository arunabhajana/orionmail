# Trash

Implemented 20 October 2026. Static checks do not establish live Gmail behavior; the checks below remain necessary before release.

## Behavior

- Trash resolves the provider's `\Trash` special-use mailbox, including localized names. Move to Trash, Restore to Inbox and Delete forever use one durable location queue.
- The folder opens cached mail immediately and uses the existing skeletons, virtualized list, paging and reading pane. Cached headers and downloaded bodies remain available offline. Mailbox history downloads fetch at most 200 headers per batch and persist a cursor after each completed batch; a later sync can resume.
- The full-list skeleton belongs to the initial local read only. An empty cache can show a non-blocking background-check state, then an empty state or loaded messages. Cached list/header reads require the unlocked active profile but do not wait for OAuth refresh. Header batches are announced before label/contact enrichment. The Trash mutation lock ends immediately after the header commit, before Gmail membership sync acquires its own commit lock; this avoids the nested-lock deadlock that previously left sync and the skeleton stuck.
- Deleting mail immediately places a normal mail card in local Trash; restoring immediately places it in local Inbox. There are no operation panels, pending banners or success toasts. Delete forever still requires confirmation. The native command saves the desired location in a short SQLite transaction and returns without waiting for OAuth, Gmail or the network mutation lock. A coalescing worker performs provider work in the background.
- Local display location is separate from the actual provider folder/UID. Cards retain their logical identity through provider UID changes. Body reads, attachments, read/unread and star actions resolve the current provider source; no synthetic Inbox/Trash UID is sent to Gmail. Known message bodies stay visible through background UID rebinding.
- An unconfirmed failure rolls back local visibility, shows a failure toast and retains the durable request for retry. Rollback exposes the current cached row only if its identity still matches; it never recreates a message the provider or a newer mailbox epoch removed. Once provider success is checkpointed, a local-write error remains pending repair instead of pretending to undo Gmail.
- Pending choices survive quitting and are retried by ordinary synchronization. Only failures show a toast, with Retry. Related failures are grouped. A subsequent move/restore replaces the desired destination of the same logical message. If an older request is still in flight, its confirmed source is checkpointed before following the newest choice. A canceled move that has not happened remotely is resolved without replaying it first.
- While Trash is active and background sync is enabled, refresh runs every 60 seconds and on focus/return online, with a 15-second throttle. It skips hidden/minimized windows. Each Trash sync reconciles cached flags and removals, so Gmail changes do not require an explicit manual refresh. This is periodic reconciliation, not instantaneous push.
- Trash has local and provider search. Gmail raw searches include Trash explicitly. Trash rows are excluded from Starred, tag views, global search and the overall unread badge. Matching stale cached aliases are removed after a successful Gmail Trash sync.

## Safety and storage

`system_mailboxes` stores the discovered role per account. `mail_location_intents` stores a stable local ID, account/message identity, current provider source, desired location, intent revision, state version, optimistic visibility, in-flight destination, errors and confirmed result. Existing Trash requests and verifiable generic pending deletes migrate transactionally into this queue. Pending work is capped at 50 logical messages per account and prevents generic cache clearing. Settled receipts retain recent UID rebinding; receipts older than 30 days are pruned at startup without deleting cached mail.

Pending source rows and their bodies remain cached but are hidden consistently from paged lists, FTS and streamed remote search results. The UI projects one normal card at the desired location. Identity follows the account and Message-ID/date/sender/subject, with source folder/UID/UIDVALIDITY for messages without Message-ID. Repeated clicks share one record. Enqueue calls are ordered per message; network work never blocks another click. Before each provider step, the worker reloads the row under the mutation lock. Revisions prevent an older failure from rolling back a newer choice, and versions prevent an older IPC reply from replacing newer state. All header ingestion uses bounded batches and releases its commit lock before label enrichment, preventing stale fetch resurrection and nested-lock deadlocks. Unread counts use the same projected locations. UI refresh notifications coalesce across rapid operations.

Commands require an unlocked application and the active account. A mailbox epoch change or ambiguous message identity stops replay. Moves use IMAP MOVE, verify one matching destination message and cache its provider-issued UID. A missing/unsafe Message-ID prevents new moves/restores before mutation. Permanent deletion requires UIDPLUS and uses UID EXPUNGE for only the selected Trash UID; it never issues bare EXPUNGE. Once a permanent delete is in flight or its outcome is uncertain, a reversal is rejected until the provider outcome is resolved. Unsupported capabilities surface a failure toast for action on the provider website.

Provider confirmation is checkpointed before local cleanup, allowing interrupted local work to finish after restart. If a request outcome was uncertain, retries check source existence first. A purge retry never follows a message out of Trash. Concurrent edits from Gmail are still possible; conflicts are retained rather than guessed away. Already accepted provider operations cannot be rolled back by closing the app.

References: [Gmail IMAP special-use folders](https://developers.google.com/workspace/gmail/imap/imap-extensions), [UIDPLUS targeted expunge](https://www.rfc-editor.org/rfc/rfc4315.html).

## Manual checks

Use disposable messages for permanent-deletion checks.

1. Restart Tauri. Open Trash: verify Gmail Trash messages load, initial loading shows skeletons, scrolling pages correctly and both cached/provider searches find expected messages.
2. Delete an Inbox message. Immediately open Trash: one normal, readable card should be there without operation text. Restore it and immediately open Inbox: the normal card should be there. Wait for Gmail and verify the final folder. Successful background completion must not show a toast or reset the reader.
3. Choose Delete forever, cancel the confirmation and verify nothing changed. Confirm on a disposable message; verify it disappears from Gmail Trash. Keep another disposable message in Trash to confirm it is unaffected.
4. Go offline and try moves/restores on several messages. Local folders should update immediately, then revert when the background connection fails, with a grouped failure toast. Fully quit/reopen, reconnect and run Sync Now. Verify the retained latest choices complete once. No success notification or operation panel should appear.
5. Delete/restore a message directly in Gmail while OrionMail Trash is visible. Wait for the next refresh (normally up to a minute), or leave and return to the app. Verify the row updates without manual Sync Now. Minimize the app and confirm returning refreshes the folder.
6. Check Starred, tags, global search and unread totals for stale Trash copies. Repeat with accounts that have colliding UIDs to check isolation. A UIDVALIDITY conflict must never apply to a reused UID.
7. Rapidly delete, restore and delete the same message while Gmail is still working; also act on several other messages. Verify one card per logical message and the final requested destination in Gmail. Refresh/search during the burst: stale sources must not flicker back. Delay/fail an older move while making a newer choice and verify it does not revert the newer choice.
8. Open a locally moved card before Gmail finishes. Check body/attachment reads and read/unread/star changes. Watch completion: the reader and flags should remain stable. Interrupt after Gmail accepts a move and verify restart finishes local repair without repeating the move. A Gmail-side restore should replace the stale Trash alias while preserving cached body bytes.

Checks performed: Rust `cargo check --offline --lib`, TypeScript and focused component lint. No automated tests added/run, and no live destructive Gmail requests performed for this implementation.
